## 主要问题

### Registry 重定向与主机校验存在安全边界缺口

**问题定性：违反硬性工程基线（公共来源访问策略的唯一实现）。**

`src/sources/fetcher.rs:321-342` 的 `is_safe_registry_token_url` 和 `is_safe_registry_redirect` 只要求目标是 `http` 或 `https`，没有像同文件 `344-367` 的 `is_safe_http_redirect` 那样检查 `require_https`。Docker 的 manifest、blob 和 token 请求走前一组函数，因此 HTTPS 上游可以把请求重定向到 HTTP 公网地址。

同一项主机判断还存在两份实现：`src/sources/fetcher.rs:369-410` 和 `src/sources/pool.rs:687-730`。后者覆盖 `100.64.0.0/10`、`198.18.0.0/15` 和 IPv4-mapped IPv6，前者没有，两份规则已经漂移。Docker 重定向使用前一份，Cargo/NuGet 等发现 URL 使用后一份，实际安全边界取决于请求走哪条路径。

两处判断都只检查 URL 主机名的字面量，不解析 DNS。若上游 Registry、Cargo index、NuGet service index 或 VS Code Marketplace 返回的主机名解析到回环、私网或链路本地地址，当前字符串检查无法阻止服务端发起请求。管理端配置的 `base_url` 是可信输入，但上游元数据中发现的下载地址和重定向目标不应被视为同等可信。

风险：被攻破或配置错误的上游可以把请求降级到明文 HTTP；tag manifest、token 等没有独立摘要锚点的路径可能遭受中间人替换；DNS 解析绕过会让上游控制的请求触达内网地址。当前没有做真实攻击复现，以上判断来自代码路径和安全策略对比。

建议：把 URL 安全策略收敛到一个模块，统一 `require_https`、私网/保留地址和重定向规则；对重定向目标解析后校验 IP，并防止 DNS 重绑定；为 HTTPS→HTTP、`100.64/10`、IPv4-mapped 和解析到私网的主机名补测试。

### 审计 JSONL 缺少跨适配器的串行化

**问题定性：违反硬性工程基线（审计事实唯一、可验证）。**

`src/audit.rs:13-15` 的 `AuditSink` 每个实例各有一把 `Mutex<()>`；`record_detailed` 在 `src/audit.rs:74-111` 对追加打开的 `File` 调用 `serde_json::to_writer`，再单独写入换行。运行期每个适配器分别构造自己的 sink：`src/service.rs:54`、`src/cargo/service.rs:82`、`src/npm/service.rs:135`、`src/nuget/service_index.rs:135`、`src/vscode/service.rs:106`、`src/docker/mod.rs:162`，后台清理也有一个 `src/retention.rs:55`。它们都写同一个 `<data_dir>/audit/events.jsonl`（`src/audit.rs:65`）。

`serde_json::to_writer` 不是一次性写完整行，而是向 writer 连续写出 JSON token。不同 sink 的互斥锁互不共享，不同生态的请求并发时，两个事件的行内容可能交错，产生无法解析的 JSONL。审计是项目声明的核心事实来源，这会让后续审计读取、清理统计和故障复盘失去可靠性。

建议：进程内共享一个 `AuditSink`，例如启动时构造 `Arc` 注入所有适配器；或使用单独写线程/队列。事件先序列化到 `Vec<u8>`，再一次性写入并换行。补一个多 sink、多线程并发写入后逐行解析的测试。当前测试只覆盖单线程轮转（`tests/retention_test.rs`），没有覆盖并发写入。

### 大对象全量进内存，文件 IO 阻塞 async worker，且缺少单飞

**问题定性：违反硬性工程基线（async 资源生命周期与阻塞 IO 边界）。**

`HttpFetcher::response_bytes`（`src/sources/fetcher.rs:217-242`）把上游响应整体读成 `Vec<u8>`。Docker blob（`src/docker/mod.rs:791`、`864-940`）、VS Code 资产（`src/vscode/service.rs:446-459`）、npm tarball、NuGet 包和 Rustup 制品都走同一模式，没有响应大小上限或流式落盘。Docker layer 常见数百 MiB 到 GiB，并发拉取时内存占用会随请求数线性增长。

请求路径中的缓存读写直接使用 `std::fs`：`src/storage.rs:296`、`src/docker/mod.rs:1524`、`src/docker/mod.rs:1783`、`src/vscode/service.rs:979`、`src/vscode/service.rs:1019`、`src/npm/storage.rs:127`、`src/nuget/package.rs:320`。后台清理 `src/retention.rs:53` 也在 `tokio::spawn` 里同步遍历和删除整棵缓存树。当前源码没有 `spawn_blocking`、`Semaphore` 或按对象键的请求合并，缓存未命中时多个客户端还会重复下载同一对象。

风险：大镜像或大 tarball 并发拉取可能触发 OOM；全量清理会占用 Tokio worker，拖慢请求；重复下载会放大上游带宽、临时文件和校验 CPU 开销。

建议：制品流式写入临时文件，边写边计算摘要，校验后原子重命名；文件 IO 放入 `spawn_blocking`；为每个生态设置并发上限，并为 artifact 对象增加单飞锁；对 metadata 响应设置合理上限。当前未做压力测试，内存和阻塞风险来自代码结构。

### Rustup manifest 的 group 404 回退与通用 SourcePool 不一致

**问题定性：规范缺失导致风险（行为契约需确认）。**

通用 `SourcePool` 对 group 的 404 会继续尝试下一个成员（`src/sources/pool.rs:322-326`），但 Rustup 的 manifest 刷新自己遍历成员（`src/service.rs:236-260`），只在 `is_retryable_source_error` 为真时继续，而该函数只匹配 `AllSourcesFailed`（`src/service.rs:313-315`）。成员作为 proxy 返回 404 时会被归类为 `TerminalSourceError`，循环立刻返回错误，后续镜像不会再尝试；checksum 请求也是同样逻辑。

这与 `docs/architecture/rustup-mvp.md:95` 的“上游顺序就是回退顺序”不一致，也与 Cargo、npm、NuGet 的 group 404 回退语义不一致。若第一个镜像缺少某个 channel，而后续镜像有该 channel，group 入口会失败。

建议：明确 404 的契约。如果 404 表示“该来源没有此对象”，Rustup 应像通用 group 一样继续；如果 Rustup 特意把 404 视为终止，应在 Rustup 文档中写明，并统一其他生态的表述。补一个“首个成员 404、第二个成员成功”的 manifest 和 checksum 测试。

### 部署模板缺少可执行前提

**问题定性：规范缺失导致风险。**

`deploy/docker-compose.yml:14-15` 使用外部网络 `stacktory`，但仓库没有说明先执行 `docker network create stacktory`。`Dockerfile:11` 创建 UID 1000 的 `stacktory` 用户，`Dockerfile:18` 以该用户运行；compose 绑定 `./app/data`、`./app/logs`，却没有设置 `user` 或说明宿主机目录需要 `chown 1000:1000`。在 Linux 上由 root 或其他用户创建的目录会让容器写入审计、缓存或日志失败。

compose 只映射 `18761:18761`；配置示例中的 Docker `listen_port`（19000 等）没有示例端口映射，标准 Docker CLI 入口按当前 compose 无法直接访问。`README.md:40` 只有一句“容器部署请使用 `deploy/app/config.example.toml`”，没有说明复制到 `deploy/app/config.toml`、创建网络、目录权限和可选端口。

建议：补一份部署说明或 README 部署段，给出可复制命令：创建外部网络、复制配置、准备目录并设置 UID 1000 权限、按需增加 `ports`，再启动 compose；为服务增加调用 `/healthz` 的 `healthcheck`。

### 工具链未固定，质量门禁只在发布 tag 触发

**问题定性：规范缺失导致风险。**

`Cargo.toml:4` 使用 `edition = "2024"`，但没有 `rust-version`；仓库没有 `rust-toolchain.toml`。`Dockerfile:1` 使用浮动的 `rust:1-slim-bookworm`，`.github/workflows/release.yml:23` 使用 `dtolnay/rust-toolchain@stable`。本地当前是 rustc 1.98.0，三个构建入口没有共同的编译器版本约束。未来 stable 变化或 Docker 基础镜像更新都可能让同一提交产生不同结果。

`release.yml` 只在 `push.tags: v*` 时运行（`release.yml:3-6`）；master 和 PR 没有 fmt、clippy、test 门禁。问题会在打 tag 时才暴露，发布流程承担了本应在合并前完成的验证。

建议：增加 `rust-toolchain.toml`，固定 channel 和 rustfmt/clippy 组件；在 `Cargo.toml` 声明 `rust-version`；固定 builder 镜像到明确版本或 digest；增加 push/PR 的 `ci.yml`，复用同一组格式、clippy 和测试命令。

### `atomic_write` 重复实现，缓存写入行为可能漂移

**问题定性：违反硬性工程基线（复用与单一实现）。**

同样的“临时文件 + rename”逻辑出现在 9 处：`src/storage.rs:352`、`src/npm/storage.rs:376`、`src/cargo/service.rs:712`、`src/vscode/service.rs:1005`、`src/nuget/package.rs:750`、`src/nuget/vulnerability.rs:633`、`src/nuget/registration.rs:709`、`src/nuget/service_index.rs:730`、`src/docker/mod.rs:1769`。它们各自选择错误类型、临时文件名和清理方式。当前行为基本一致，但没有共享不变量；后续如果补 `fsync`、权限或跨平台 rename 处理，需要改 9 个地方，容易出现某个生态仍写半成品。

建议：在 `storage` 或新的 `fsutil` 中提供一个原子写入实现，各适配器只在边界做错误映射；为临时文件残留、rename 失败和并发覆盖补一组共享测试。

### 大型适配器模块职责过宽

**问题定性：建议优化。**

`src/docker/mod.rs` 1791 行，`src/vscode/service.rs` 1052 行，`src/npm/service.rs` 887 行，`src/nuget/package.rs` 870 行。以 Docker 为例，同一文件同时承担路径解析、manifest/blob 校验、上游获取、缓存元数据、查询分页、响应头和审计。协议适配器本身复杂，但当前边界让任何一处协议变化都要在大文件中定位。

建议：按“路径与协议解析、对象校验、缓存元数据、响应构造”拆分子模块；先拆 Docker 的 manifest/blob/query，再根据实际增长处理 VS Code 和 npm。拆分属于后续结构收敛，不建议与本次安全和资源修复混在一起。

### 配置和路径段校验存在缺口

**问题定性：规范缺失导致风险。**

`RawConfig` 和 `RawSourceConfig`（`src/config.rs:284`、`src/config.rs:329`）没有 `deny_unknown_fields`，TOML 反序列化会静默忽略未知键。`retention`、`source`、`channel` 等可选字段拼错时，服务会按默认值启动，管理端很难发现配置没有生效。

`is_valid_source_name` 和 `is_valid_channel`（`src/config.rs:496-508`）只限制字符集，允许 `.` 和 `..`；`storage::validate_source_name` 与 `validate_channel`（`src/storage.rs:317-338`）也一样。这些值会拼进 `stores/<ecosystem>/...` 路径（`src/layout.rs`），例如 source 名为 `..` 时，`metadata_root` 或 `artifact_objects_root` 的路径会越过预期的生态子目录。管理端配置是可信输入，但这里缺少的是防御性校验，不应让合法字符集破坏路径语义。

`[pypi]` 在 `src/config.rs:21`、`400`、`420` 被解析，但 `src/main.rs:119` 的 `configured_registry` 不注册 PyPI；README 又说 PyPI 不可用。管理员配置后不会收到启动警告，只会得到 404。示例配置里仍保留 `[pypi]` 段，增加了误配置概率。

建议：对可加的结构使用 `deny_unknown_fields`（注意 `RawDockerSourceConfig` 的 flatten），或在启动时打印未识别键；路径段校验拒绝 `.` 和 `..`；PyPI 未实现前在配置解析阶段直接拒绝 `[pypi]`，或至少打印明确警告，并从示例中移除该段。

### 示例配置中的上游主机需要核对

**问题定性：建议优化（需确认）。**

`deploy/app/config.example.toml:102-104` 把 `https://downloads.unstructured.io` 作为 Docker source，`deploy/app/config.example.toml:140-147` 把 `https://cdn.npmmirror.com/binaries` 作为 npm source。按当前适配器的协议假设，Docker source 需要 Registry V2 根，npm source 需要 npm registry；这两个主机从用途看更像文件或二进制 CDN，不是对应协议的根地址。它们被放进 group 后，正常请求会先得到无效响应再回退，增加延迟和误判。

建议：确认这是有意的协议入口还是历史配置。若不是，从示例 group 中移除，或在注释中说明它们只用于特定对象、不参与该 group。此处未对公网主机做实际探测。

### CORS、健康检查和关闭流程偏宽松

**问题定性：建议优化。**

`src/http.rs:122-127` 对任意 `Origin` 反射 `Access-Control-Allow-Origin`，同时设置 `Access-Control-Allow-Credentials: true` 和 `Access-Control-Allow-Private-Network: true`。当前服务没有认证，风险有限；一旦后续加入凭据或内网权限，这组策略会让任意网页读取服务响应。

`src/http.rs:91-92` 的 `/healthz` 恒返回 200，不检查数据目录可写性或上游状态；`src/main.rs:63` 直接 `axum::serve(...).await?`，没有 `with_graceful_shutdown`。Docker 停止时进程会被直接终止，正在写入的临时文件或审计行可能中断。原子写入降低了损坏概率，但没有让关闭过程可观测。

建议：按实际客户端需求收窄 CORS，至少在加入认证时移除 `credentials` 或限制 Origin；区分 liveness 和 readiness，readiness 检查 `data_dir` 可写；为 SIGTERM 增加优雅关闭并让后台清理任务退出；compose 增加 `/healthz` 健康检查。

### 仓库治理缺少敏感环境文件和换行约束

**问题定性：规范缺失导致风险。**

`.gitignore` 未包含 `.env` 或 `.env.*`；`.dockerignore` 已包含。如果后续在 `deploy/` 放环境文件，可能被误提交。仓库没有 `.gitattributes`，当前 122 个跟踪文件都是 LF（`git ls-files --eol`），但 Windows 协作下缺少换行约束。

建议：补 `.env` 忽略规则和 `.gitattributes`，至少约束 `*.rs text eol=lf`。

### 遗留公共 API 和未使用状态

**问题定性：建议优化。**

`src/http.rs:24` 的 `pub fn router()` 只在 `tests/http_test.rs:28` 中使用；`src/http.rs:50` 的 `router_with_rustup_and_cargo`（`src/lib.rs:28` 导出）没有调用方；`DockerService` 的 `_root_url`（`src/docker/mod.rs:37`、`161`）也没有使用。它们扩大了公共 API 和状态面，容易让后续维护者误以为这些入口仍受支持。

建议：删除或标记测试专用的遗留路由，移除未使用的 Docker 字段和参数。

- 合并 `atomic_write`。
- 拆分 Docker 等超大适配器模块。
- 补配置校验、示例配置核对、CORS/健康检查/优雅关闭、仓库治理和遗留 API 清理。
