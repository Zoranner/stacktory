# Stacktory 数据目录设计评审报告

## 评审范围

本次只评审 `data_dir` 下的缓存、快照和审计文件组织，不评价未实现生态的协议功能，也不评价业务规则。

## 评审依据

- 当前 Rust 服务的 `src/storage.rs`、`src/service.rs`、`src/cargo/service.rs`、`src/vscode/service.rs` 和 `src/audit.rs`。
- 当前根配置 `config.toml` 中的 `data_dir = "data"`。
- 当前 README 与生态架构文档。
- 当前运行目录中的 Rustup、Cargo 缓存与审计文件。

## 总体结论

当前数据目录的状态所有权划分已经合理：

- Rustup snapshot、Cargo index、VS Code metadata 由命名入口拥有，按 `{entry}` 隔离。
- Rustup dist、Cargo crate、VSIX 是已校验的二进制对象，由实际 `{proxy}` 拥有，不再由 `group` 或入口名拥有。
- 写入采用临时文件后重命名，公开 snapshot 通过 `current.toml` 指针切换，避免读取半成品。
- 根目录 `data/` 已被 `.gitignore` 排除，不会作为仓库产物提交。

但当前设计只有对象归属，没有数据生命周期。单机 MVP 可以运行；长期服务还缺少容量、淘汰、审计轮转和旧布局清理机制，因此不能称为完整的可持续数据管理方案。

## 检查情况

- 当前运行数据存在：
  - `data/rustup/snapshots/{entry}/{channel}/{revision}/...`
  - `data/rustup/artifacts/{proxy}/objects/{dist-path}`
  - `data/cargo/metadata/{entry}/index/...`
  - `data/cargo/artifacts/{proxy}/objects/crates/...`
  - `data/audit/events.jsonl`
- 已验证 Rustup 与 Cargo 从 `group` 切换到同一实际 proxy 时复用 source-owned artifact，不重复写入对象。
- 已检查当前目录仍残留旧布局的 Rustup 与 Cargo artifact 文件；新代码不读取这些路径。

## 主要问题

### 缺少容量和淘汰策略

**问题定性：规范缺失导致风险。**

当前 snapshot 按 revision 永久累积，artifact、Cargo index、crate 与 VSIX 也没有最大容量、最大版本数、最长未访问时间或过期清理策略。`data/audit/events.jsonl` 同样只追加、不轮转。

长期运行后，nightly Rustup manifest、频繁依赖下载和审计事件会持续增长，最终把容量压力转移给宿主机和部署运维。

建议先明确最小运维契约：

- 每个 Rustup `{entry}/{channel}` 保留的 snapshot revision 数。
- artifact 总容量或按 proxy 的容量上限。
- metadata/index 的 TTL 与过期清理规则。
- JSONL 审计的按日期轮转、保留天数和归档策略。

这些规则应由服务配置或明确的维护命令承载，不能依赖人工发现磁盘满后再删除目录。

### 旧 artifact 布局仍占用磁盘

**问题定性：规范缺失导致风险。**

当前新布局为 `{proxy}/objects/...`，旧布局没有 `objects` 层，代码不会读取旧文件。但运行目录仍存在旧的：

```text
data/rustup/artifacts/group/stable/...
data/rustup/artifacts/aliyun/stable/...
data/cargo/artifacts/group/crates/...
```

这些文件不会影响新缓存正确性，却会重复占用磁盘。当前代码没有一次性的清理入口，也没有部署升级时的清理说明。

建议提供一个明确、只删除旧布局的维护命令，删除规则固定为“`artifacts/{source}/objects` 之外的旧 artifact 子树”，并在部署升级说明中标注其影响范围。该命令不应触及 snapshot、metadata、审计或新对象缓存。

### README 仍描述旧的单一来源快照模型

**问题定性：规范缺失导致风险。**

README 当前仍说明 group 刷新选中一个 proxy 后，后续 artifact 只访问该 proxy。现有 Rustup snapshot 已改为为每个 artifact 保存 `checksum + source_name`，同一 manifest 可以绑定多个已声明 proxy。

数据目录职责已按每个 artifact 的实际 source 划分，但运行说明仍保留旧模型，会让部署者误判缓存复用、来源切换和故障排查行为。

建议将 README 与 Rustup 架构文档统一为“manifest 入口级、artifact source 级”的状态模型，并明确 `group` 不进入 artifact 缓存键。

### 二进制对象并发下载缺少对象级合并

**问题定性：建议优化。**

当前原子写入保证不会公开半文件，但 Rustup、Cargo 与 VSIX 的相同未命中对象没有对象级下载锁。多个并发请求可同时从上游下载同一对象，最后由原子重命名竞争发布。

这不会破坏内容完整性，但在大制品、慢速镜像或大量客户端同时冷启动时会放大带宽、上游连接和本地临时文件压力。

建议在后续容量治理一起增加以 `{ecosystem, proxy, object-key}` 为键的进程内合并锁；锁只覆盖未命中的下载与发布，不锁缓存命中读取。

## 整改优先级建议

### 先固化数据生命周期

- 定义 snapshot、artifact、metadata 与审计的保留上限和淘汰触发时机。
- 提供可审计的清理命令或维护子命令。
- 先清理当前旧 artifact 布局，回收重复空间。

### 再控制冷缓存并发压力

- 对同一 artifact 的未命中下载进行请求合并。
- 将下载次数、缓存命中率、缓存目录大小和清理结果纳入审计或运行指标。
