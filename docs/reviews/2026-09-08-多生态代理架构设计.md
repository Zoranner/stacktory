# Stacktory 工程评审报告

## 评审范围

本次评审对象为 `docs/architecture/multi-ecosystem-readonly-proxy.md`，
重点检查多生态只读代理的工程架构、配置模型、协议适配边界、缓存与回退模型、
路由迁移和后续扩展能力，不评价各生态当前是否已经实现。

## 评审依据

- 当前仓库 `Cargo.toml`、`src/`、`tests/` 和已有 Rustup MVP 实现。
- 当前架构设计文档 `docs/architecture/multi-ecosystem-readonly-proxy.md`。
- 当前 Rustup 对外路由 `/mirror/rustup/dist/**` 及配置字段
  `rustup.upstreams`。
- 本次评审采用的工程评审基线：职责边界清晰、公共契约稳定、配置与文档一致、
  安全边界可验证、缓存和回退语义明确、验证路径可执行。
- Cargo Registry Index、npm package metadata、PyPI Simple API、NuGet V3
  service index 的官方协议说明。

## 总体结论

当前设计已经形成了正确的总体方向：生态协议独立适配，公共层复用来源访问、
缓存、完整性和审计；`proxy` 与 `group` 的类型模型也适合表达独立代理和显式
组合入口。每个 `proxy` 只配置一个远程仓库地址，协议内部的资源路径由对应
适配器处理，不需要把一个仓库拆成多个地址配置。

但当前文档还不能直接作为实施依据。配置模型和请求状态模型仍缺少几个决定性
契约，直接编码会导致 Cargo、NuGet 以及 npm/UPM 的缓存一致性在实现阶段重新
返工。数据库在当前只读代理范围内没有必要，文件系统足以承担配置、缓存、快照
和审计存储。

评审结论：**设计方向可保留，实施前需要先修订文档中的高风险问题。**

## 主要问题

### 高：group 回退缺少元数据与制品的来源绑定

**问题定性：规范缺失导致风险。**

设计文档第 38-55 行规定 group 按成员顺序回退，第 397-432 行又规定元数据和
制品请求都按 sources 顺序访问。但文档没有定义：

- 元数据由哪个成员成功返回。
- 元数据中列出的制品后续是否必须从同一成员获取。
- 元数据来源不可用后，是否允许改用另一个成员。
- 两个成员内容不一致时，哪个版本、摘要或链接具有权威性。

对于 npm metadata、PyPI 项目索引、NuGet registration 和 Cargo index，这不是
普通文件代理问题。一个来源返回的元数据可能引用其自身的包存储、版本集合或
摘要；后续制品请求若重新从 group 第一成员开始，可能得到另一来源的内容。

**风险：**

- 元数据和制品来自不同仓库，内容摘要不匹配。
- 私有包源的包名或版本集合被错误地与公共源混合。
- 同一个 group 在不同请求中表现不稳定，难以审计和复现。

**建议：**

在设计中明确 source affinity。至少需要一种可验证的策略：

1. 元数据命中某个 proxy 后，元数据中重写的制品 URL 带上稳定的逻辑对象引用，
   服务端根据该引用绑定原始 proxy。
2. 或将来源选择结果写入缓存元数据，后续制品请求优先使用原 source；原 source
   失败时只有在重新校验摘要后才允许回退。
3. 对 group 中内容不一致的来源，明确是“首个成功来源优先”还是“按摘要合并”，
   不允许由实现者临时决定。

审计至少应记录 logical source、selected proxy 和 fallback chain，不能只记录
一个笼统的 `source`。

### 中：缓存键没有包含命名入口、协议变体和响应表示

**问题定性：规范缺失导致风险。**

设计文档第 146-165 行把 metadata 和 artifact 抽象为公共缓存，第 397-424 行
使用“逻辑对象键”描述缓存，但没有定义键的组成。

当前入口模型中，同一生态可以有多个 proxy/group；PyPI 同一个项目还可能有
HTML 和 JSON 两种表示；npm metadata 受 `Accept` 影响；NuGet 的不同资源类型
也可能共享相似路径。只用 package/path 作为键会造成跨入口或跨表示污染。

**建议：**

固定缓存键至少包含：

```text
ecosystem
entry_name
protocol_variant
object_key
representation
```

其中 `entry_name` 是客户端访问的 proxy/group 名称，`protocol_variant` 用于
区分 Cargo sparse、NuGet resource 等协议角色，`representation` 用于区分
PyPI HTML/JSON、npm metadata 变体等响应表示。缓存文件布局和审计对象键应采用
同一逻辑键规则。

### 中：group 成员引用和嵌套规则未定义完整

**问题定性：规范缺失导致风险。**

设计文档第 72-82 行允许 group 引用同一生态下的 source，但没有说明：

- `members` 是否只能引用 `proxy`。
- 是否允许 group 引用 group。
- 是否允许重复成员。
- 是否允许自引用。
- 如何检测多级循环。
- group 是否必须至少包含一个成员。

第 151-164 行又要求 `SourcePool` 接收“解析后的有序 proxy 列表”，这实际上暗示
group 最终只能展开为 proxy，但没有把它写成配置约束。

**建议：**

首期固定为：group 只能引用 proxy，不允许嵌套 group；成员非空、不能重复；
引用必须存在且属于同一生态。未来确实需要嵌套时，再引入有界展开和循环检测，
不要在首期留下模糊递归语义。

### 中：配置示例与命名规则仍有漂移

**问题定性：违反项目已确认规范。**

设计文档第 67 行规定 `name` 在当前生态内唯一，并允许短名称；但第 301-307
行仍使用 `pypi-official`，而 Rustup、Cargo、npm 示例改用了 `official` 和
`group`。这会让读者无法判断短名称是推荐规范还是仅用于部分生态。

同时，当前代码仍使用 `upstreams`，而文档第 318-320、436-444 行要求迁移到
`sources`。这本身可以作为待实施迁移，但配置示例应明确标注“目标 schema”，
并在迁移计划中列出旧字段废弃和错误提示。

**建议：**

- 统一示例使用 `official`、`internal`、`group` 等生态内短名称。
- 明确 `name` 的字符集、大小写、保留字和 URL 编码规则。
- 明确 `type` 是反序列化枚举，不接受未知值。
- 为 `proxy`/`group` 的互斥字段写出配置校验表。

### 中：缓存 TTL 语义使用 `-1` 和 `0`，但没有统一不变量

**问题定性：规范缺失导致风险。**

设计文档第 208-215 行使用：

```toml
metadata_ttl_secs = 86400
artifact_ttl_secs = -1
negative_ttl_secs = 86400
```

随后用文字说明 `-1` 和 `0`，但没有定义字段类型、允许范围、默认值、过期时
是否后台刷新、旧值是否可用，也没有说明 `negative_ttl_secs` 是否启用负缓存。

**建议：**

在公共配置契约中固定：

- 允许值及其 TOML 类型。
- `0`、正数、`-1` 的精确定义。
- 元数据过期和制品过期是否分别允许 stale serving。
- 负缓存是否需要独立的启用字段。
- 测试覆盖每种值和服务重启后的行为。

## 整改优先级建议

### 实施前必须完成

- 明确 group 的来源绑定和跨来源一致性规则。
- 固定 group 成员只能引用 proxy，或完整定义嵌套 group 展开和循环检测。
- 固定缓存键组成，避免入口、协议变体和响应表示之间的污染。

### 公共架构基座阶段

- 将配置模型实现为 `type` 枚举和经过校验的 source graph。
- 将来源访问、单一远程地址、逻辑入口和适配器协议职责拆开。
- 为 group resolution、source affinity、缓存键和新路由配置增加独立测试。
- 将当前 Rustup 迁移作为单独可审查逻辑单元，不与 Cargo 适配器同时隐藏完成。

### 生态适配器阶段

- Cargo 先实现 Sparse Index 的实际 `config.json`、index 记录和下载入口契约。
- npm 与 UPM 共用协议核心，但分别定义路由、scope 和入口配置。
- PyPI 先固定 HTML/JSON 表示和 `Accept` 协商的缓存键。
- NuGet 以 service index 资源发现为中心实现地址校验与重写，搜索保持独立。
