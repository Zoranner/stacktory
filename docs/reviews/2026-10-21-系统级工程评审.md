## 主要问题

### group 故障转移策略已统一，但执行模型仍分散在适配器

**问题定性：违反硬性工程基线（复用与单一实现）。**

`src/sources/fallback.rs` 已经统一了 `401`、`403`、`404`、`408`、`429`、`5xx` 和网络失败的分类，但真正执行 group 回退的循环仍分布在各生态：

- 通用路径请求在 `src/sources/pool.rs:366` 的 `fetch_request` 中循环。
- Rustup manifest 在 `src/service.rs:262` 自己遍历成员。
- Cargo 在 `src/cargo/service.rs:194` 和 `:374` 分别遍历索引和制品。
- npm 在 `src/npm/service.rs:250`、`:299`、`:377`、`:505` 分别遍历 ping、search、metadata、tarball。
- NuGet 在 `src/nuget/service_index.rs:221`、`src/nuget/registration.rs:112`、`src/nuget/package.rs:73` 和 `:234`、`src/nuget/search.rs:50`、`src/nuget/vulnerability.rs:119` 和 `:293` 分别遍历。
- Docker 在 `src/docker/mod.rs:1720` 生成候选来源，并在 catalog、tags、manifest、blob、search 中分别循环。

“优先使用绑定来源”“全部 404 才返回 404”“协议响应无法解析时是否换来源”“是否记录 fallback 审计”等规则仍由每个循环自行维护。最近一轮修复中出现的 Cargo 制品 `403` 不回退、NuGet 搜索 `401/403/404` 不回退、Rustup 直接来源 `404` 语义不一致，都是这种重复执行模型已经产生漂移的证据。

风险：后续调整回退状态、候选顺序、404 汇总或审计字段时，需要同时修改多个适配器；某个生态漏改时，测试只覆盖局部，线上表现为“同一个 group 在不同制品类型下行为不同”。

建议：把 group 的候选执行收敛为共享层，例如“有序候选 + 绑定来源优先 + 失败分类 + 全部 404 汇总 + 标准回退审计”的执行器。适配器只提供协议对象键和响应校验函数，不再重复编写成员循环。该收敛不需要新增配置，也不改变现有 `members` 语义。

### 缓存没有统一的身份和生命周期

**问题定性：违反硬性工程基线（状态与缓存一致性）。**

当前缓存至少存在三条互不一致的生命周期路径。

第一，来源配置变更不会失效一部分已缓存的 metadata。这里需要先限定范围：按 digest、checksum 或内容哈希寻址的 artifact 缓存不应因为 `base_url` 变化而失效；受影响的是缓存中保存了由 `base_url` 派生出的绝对上游地址，或保存了可变引用（例如 Docker tag 到 digest 的映射）的 metadata 和来源绑定。`src/main.rs:20` 的标记文件只保存 `root_url`，`src/main.rs:82` 只在 `root_url` 变化时清理 metadata 和 Rustup 快照。NuGet service index 缓存只检查 `selected_proxy` 名字是否仍在成员中（`src/nuget/service_index.rs:186`），不检查该来源当前的 `base_url`；Docker manifest/tag 绑定只检查来源名（`src/docker/mod.rs:574`）。当管理员修改某个 proxy 的 `base_url` 而名称不变时，这些仍指向旧上游的 registration、package、tag 或 tarball 描述符会被继续读取。旧 URL 如果与新 `base_url` 不同源，会在 `src/sources/pool.rs:730` 的 `valid_discovered_url` 处失败，表现为持续 `502`；如果只是同源路径变化，则可能继续访问旧路径，表现为静默读错上游。Cargo index、Rustup 快照和 VS Code 的部分缓存是否受 `base_url` 影响，要按各自保存的是本地重写地址、校验和还是外部绝对地址分别判断，不能统一按“所有缓存都失效”处理。

本次已在 npm/UPM 落地 canonical metadata、来源指纹和按 `root_url` 渲染，npm/UPM 不再属于这条缓存身份问题。下面列出的剩余风险集中在 NuGet、Docker、Rustup 以及尚未实现的内容寻址 artifact 迁移。

第二，metadata 和 artifact 的保留窗口不同，但 artifact 请求依赖 metadata 描述符。`src/retention.rs:294` 按 `metadata_ttl_secs`（默认 7 天）删除 metadata，`src/retention.rs:320` 按 `artifact_idle_secs`（默认 90 天）淘汰 artifact。Docker blob 请求先读 `read_blob_metadata`，找不到描述符就直接返回 `UnknownBlob`（`src/docker/mod.rs:841`）；npm tarball 先读 descriptor（`src/npm/service.rs:488`）；NuGet package 先读 binding。描述符过期后，实际制品文件仍在缓存中，但直接按 digest 或 artifact key 请求会返回 `404`/`UnknownArtifact`，需要重新拉取 metadata 才能恢复。这使“缓存还在”和“服务能命中”不是同一件事。

第三，损坏缓存的恢复策略不一致。Cargo 会在发现索引缓存不可解析时删除并重新获取（`src/cargo/service.rs:148`）；npm metadata 已在本次整改中改为自愈；NuGet descriptor 解析失败直接返回 `Serialization`（`src/nuget/service_index.rs:663`），Docker manifest metadata 解析失败返回 `Serialization`（`src/docker/mod.rs:1474`）。这些未迁移路径最终通常是 `500`，而不是当作缓存未命中重新获取。一次不完整写入、旧 schema 或人工改坏一个描述符，就可能让对应入口持续失败到清理任务或人工删除为止。

风险：来源迁移、镜像地址调整、磁盘异常或版本升级后，服务可能持续返回错误或读取旧上游；运维只能通过清缓存或等 TTL 恢复。

建议：为缓存建立统一身份和生命周期契约，但只对受影响的 metadata 和来源绑定建立配置指纹，不要无差别清理内容寻址的 artifact 缓存。至少在指纹中加入 `root_url`、各 proxy 名称与 `base_url`、`require_https`；把 metadata 描述符的解析失败统一视为无效缓存并删除重建；让 artifact 绑定描述符与 artifact 使用同一淘汰窗口，或让 artifact 查询具备不依赖短 TTL metadata 的自描述能力。补“修改 base_url 后不命中保存了旧绝对地址的 metadata”“修改 base_url 后内容寻址 artifact 仍可命中”“描述符损坏后自动重建”“metadata 过期但 artifact 仍可直接命中”的测试。

### 按对象键创建的互斥锁表没有回收

**问题定性：违反硬性工程基线（资源生命周期）。**

`src/service.rs:27` 和 `:28` 维护 `refresh_locks`、`artifact_locks`，`src/service.rs:129` 和 `:137` 在每次请求时按来源、channel 或 DistPath 插入新的 `Arc<Mutex<()>>`；`src/docker/mod.rs:52` 维护 `blob_locks`，`src/docker/mod.rs:1044` 按 repository 和 digest 插入。源码中没有对应的删除或弱引用回收路径。

这些 map 的键属于外部输入空间：每个不同的 Rustup 制品路径、每个不同的 Docker blob digest 都会永久新增一个条目。它们不会随 artifact 缓存淘汰而消失，也不受 `artifact_idle_secs` 控制。长期运行的公开镜像入口会随唯一对象数量线性增长内存；这不是单个对象大小的问题，而是对象数量累积的问题。

风险：服务运行时间越长、拉取过的镜像和工具链版本越多，内存越高；清理磁盘缓存不会回收这部分状态，重启才能释放。

建议：改为固定分片的锁表（按 key 哈希到有限数量的 `Mutex`），或使用带引用计数的锁管理器并在最后一个等待者退出后移除条目。补一个批量生成不同 key 后锁表规模不随 key 数量无限增长的测试。该调整不改变单飞语义。

### 制品路径缺少统一的资源模型

**问题定性：违反硬性工程基线（async 资源生命周期与并发预算）。**

当前大对象的处理方式按生态分裂：

- Docker blob 已使用 `response_file` 流式落盘（`src/sources/fetcher.rs:404`），但通用 `response_bytes` 仍把响应整体读入 `Vec<u8>`（`src/sources/fetcher.rs:378`）。
- npm tarball、NuGet package、Cargo crate、Rustup dist 和 VS Code 资产仍以 `Vec<u8>` 返回并整体写入缓存，缓存命中时再次整体读取。
- `src/storage.rs:291` 的 `get_verified`、`src/docker/mod.rs:1651` 的 `read_verified_artifact_path`、`src/npm/storage.rs:106` 的 `read_verified_artifact`、`src/nuget/package.rs:629` 的 `cache_is_valid` 都会在每次命中时重新计算完整摘要。Docker layer 常见数百 MiB 到 GiB，命中一次就要完整读盘并哈希一次，然后才能开始响应。
- `src/sources/pool.rs:25` 的 artifact 并发上限是每个 `SourcePool` 4 个；`src/main.rs:202` 起为每个生态分别创建 `SourcePool`，因此实际全局 artifact 并发是“4 × 生态数”，没有跨生态的统一预算。

风险：大 tarball、NuGet 包、VSIX 或工具链制品会造成内存峰值和读放大；缓存命中延迟接近完整读取一遍对象；多个生态同时拉取时可能同时占用网络、磁盘和上游带宽，缺少全局背压。

建议：统一 artifact 路径为“流式写入临时文件、边写边算摘要、校验后原子发布”；缓存命中优先信任发布时记录的摘要和文件元数据，把全量重算降为可选的定期校验，而不是每次请求的固定成本；artifact 并发使用共享的全局预算，并按生态保留公平性。该收敛不新增用户配置。

### 错误分类仍混用客户端错误和上游响应错误

**问题定性：违反硬性工程基线（错误边界与协议状态）。**

至少有三处错误分类会直接影响客户端行为和 group 回退：

- VS Code query 的响应 JSON 在 `src/vscode/service.rs:625` 用 `serde_json::from_slice(source)?` 解析，`serde_json::Error` 被映射为 `VscodeError::RequestJson`；`src/vscode/service.rs:950` 又把 `RequestJson` 映射为 `400`。上游返回 200 但响应不是合法 JSON 时，客户端得到的是“请求错误”，而不是“上游响应错误”，也没有进入 group 的下一来源。
- NuGet 搜索把客户端 query 校验失败和上游搜索响应结构失败都归为 `NugetError::InvalidSearch`（请求侧见 `src/nuget/search.rs:34`，响应侧见 `:170` 等）；`src/nuget/search.rs:327` 把它映射为 `400`。直接来源返回不可解析的 search 响应时，客户端看到 `400`；只有 group 全部失败时才可能变成 `502`。
- Rustup 的 `service_error_response` 只把 `UnknownEntry` 映射为 `404`，其他 `ServiceError::Source(_)` 统一映射为 `502`（`src/http.rs:246`）。直接来源明确返回 `404` 时，客户端得到的是 `502`，与其他生态“直接来源保留上游状态”的约定不一致。

风险：客户端会把上游故障当成自己的请求错误，可能停止重试或错误提示；监控无法区分“请求非法”和“上游响应损坏”；同一 group 在不同生态下返回不同状态码。

建议：在错误枚举中明确区分 `InvalidRequest` 与 `InvalidUpstreamResponse`；上游解析失败、完整性失败和协议关系失败统一映射为 `502` 并参与 group 回退；直接来源的明确 `4xx` 保留原状态。补直接来源和 group 两条路径的状态码测试。

### Rustup group 的制品回退仍不完整

**问题定性：规范缺失导致风险（跨生态 group 契约未统一）。**

Rustup manifest 刷新已经按 group 成员回退，但制品下载在 `src/service.rs:155` 的 `artifact_for_request` 中只使用 `StoredSnapshot.artifact_sources` 记录的 `selected_source`，没有按 group 成员继续尝试。manifest 已经为每个制品保存了 SHA-256 和来源绑定，因此“换一个成员下载并用同一 checksum 验证”在协议上是可行的。

其他生态的制品路径已经支持“绑定来源优先，失败后按 group 顺序尝试下一个来源”：Cargo 在 `src/cargo/service.rs:374` 起、npm 在 `src/npm/service.rs:505` 起、NuGet 在 `src/nuget/package.rs:234` 起、Docker 在 `src/docker/mod.rs:909` 起都有成员循环。Rustup 是例外。

风险：manifest 从镜像 A 成功获取，但 A 缺少某个具体制品，而镜像 B 有同一制品时，Rustup group 仍然失败；用户需要手工切换到 B 或重新刷新来源。这与“group 是故障转移入口”的整体预期不一致。

建议：明确 Rustup 制品是否参与 group 回退。如果参与，使用当前制品的 SHA-256 遍历剩余成员，验证成功后更新该制品的来源绑定和缓存；如果不参与，在 Rustup 架构文档中写明这是刻意例外，并在审计中记录“未尝试其他成员”的原因。该选择不需要新增配置。

### 审计回退链没有按架构契约完整记录

**问题定性：违反项目已确认规范（审计事实要求）。**

`docs/architecture/multi-ecosystem-readonly-proxy.md:239` 要求审计至少记录入口、协议对象、`selected_proxy`、回退链、类型、cache 状态、发布结果和失败类别。实际实现只在部分适配器中记录回退：

- 通用 `SourcePool` 的 group 循环（`src/sources/pool.rs:366`）没有 `AuditSink`，失败成员只被拼进错误字符串；成功返回后这些失败信息被丢弃。
- Rustup manifest 在 `src/service.rs:262` 收集 `failures`，但成功时直接 `return Ok((member.name, rewritten))`，失败成员不写审计。
- npm metadata 在 `src/npm/service.rs:377` 收集失败，成功时只记录 `metadata_published` 和最终来源，不记录前面的失败成员。
- Docker、Cargo 和部分 NuGet 路径会写 `*_fallback` 或 `*_fetch_failed` 事件，字段和事件命名又各不相同。

风险：线上出现“第一个镜像 429、第二个镜像成功”时，审计只能看到最终成功来源，无法还原回退链，也无法统计某个镜像的失败率。这对当前正在处理的镜像限流和故障转移问题尤其不利。

建议：由共享 group 执行器统一写标准回退事件，或在公共层提供审计回调，要求每个适配器在成员失败时记录“来源、对象、状态、失败类别、是否继续”。补一个“首个成员失败、第二个成员成功”的审计契约测试，验证事件中能还原完整回退链。

### 公共契约文档与实际实现存在漂移

**问题定性：违反项目已确认规范（文档与代码一致性）。**

两处会直接影响运维判断：

- `README.md:53` 说明 `proxy_no_proxy` 与 `NO_PROXY` 同时存在时 `NO_PROXY` 优先；`src/sources/fetcher.rs:142` 实际先使用配置中的 `proxy_no_proxy`，只有它为空时才调用 `reqwest::NoProxy::from_env`。即配置优先，文档写反了。
- `docs/architecture/multi-ecosystem-readonly-proxy.md:217` 声明公共 TTL 语义支持正数、`0` 和 `-1`，但 `src/config.rs:39` 的 `metadata_ttl_secs` 是 `u64`，`src/config.rs:402` 明确拒绝 `0`，配置层没有 `-1` 表示。`src/retention.rs:294` 实际只把该值当作 metadata 删除窗口，不是请求路径的缓存 TTL。后文 `docs/architecture/multi-ecosystem-readonly-proxy.md:259` 又把它解释为保留上限，前后语义不一致。

风险：管理员会按文档配置不存在的 TTL 行为，或在代理排障时误判优先级；缓存策略的理解会偏离实际实现。

建议：以当前实现为准修正文档，明确 metadata TTL 是清理窗口而非请求 TTL，明确 `proxy_no_proxy` 的优先级；如果确实需要 `0/-1` 语义，再单独设计配置契约，不在此次评审中默认增加配置。

### 运行时可观测性和关闭流程仍有缺口

**问题定性：规范缺失导致风险。**

`src/http.rs:91` 的 `/healthz` 恒返回 `200`，不检查数据目录或日志目录可写性，也不区分 liveness 和 readiness。`src/main.rs:66` 为 Docker 标准端口启动的监听任务只调用 `axum::serve(...)`，没有接入主服务的 `with_graceful_shutdown`。`deploy/docker-compose.yml` 没有配置 healthcheck。

风险：容器可能显示为运行中，但数据目录不可写或标准 Docker 端口没有正常服务；停止容器时，Docker 监听上的在途请求不会像主监听那样收到优雅关闭信号。服务也没有请求延迟、上游失败率和回退次数的指标，镜像限流问题只能靠审计和日志间接排查。

建议：增加 readiness 检查（至少验证 `data_dir` 和 `log_dir` 可写），让所有 Docker 监听共享关闭信号，compose 使用 `/healthz` 做健康检查。指标可以先从审计事件和日志中派生，不引入新的外部依赖。

### 仓库治理的低优先级缺口

**问题定性：规范缺失导致风险。**

`.gitignore` 没有覆盖 `.env` 或 `.env.*`，虽然当前仓库没有跟踪环境文件；仓库也没有 `.gitattributes`，当前 128 个跟踪文件都是 LF，但 Windows 协作下缺少换行约束。`.dockerignore` 已覆盖 `.env`，说明容器构建边界和 Git 边界不一致。

风险：后续在 `deploy/` 放置环境文件时可能误提交；不同开发机的换行设置可能制造无意义 diff。

建议：补 `.env` 忽略规则和最小 `.gitattributes`（至少约束 Rust、TOML、Markdown 为 LF）；不引入 Git LFS，当前没有大体积二进制资源。

## 整改优先级建议

### 先收敛缓存与来源配置的身份

- 为 `root_url`、proxy 名称、`base_url`、`require_https` 建立配置指纹，变更时清理受影响的 metadata 和来源绑定。
- 统一 metadata 描述符损坏时的处理：删除或隔离后重新获取，不把缓存解析失败直接变成永久 `500`。
- 统一 artifact 描述符与 artifact 的淘汰窗口，或让 artifact 查询不依赖短 TTL metadata。

### 再收敛 group 执行模型

- 提取共享的 group 候选执行器，统一“绑定来源优先、成员顺序、全部 404 汇总、协议错误回退、标准审计事件”。
- 各适配器只保留协议对象键和响应校验，不再重复维护成员循环。
- 为直接来源、group、绑定来源三种入口分别补状态码和回退行为测试。

### 处理资源生命周期

- 把按对象键创建的锁表改为固定分片或可回收的锁管理器。
- 让 npm、NuGet、Cargo、Rustup 和 VS Code 的大对象走流式落盘，避免完整响应进入内存。
- 评估缓存命中全量重算摘要的成本，把“发布时校验 + 命中时信任元数据 + 定期校验”作为统一策略。
- 为所有生态建立共享的 artifact 并发预算，避免每个生态各自占用 4 个上游连接。

### 最后统一错误、审计和文档

- 拆分客户端请求错误和上游响应错误，修正 VS Code、NuGet search 和 Rustup 的状态映射。
- 明确 Rustup 制品是否参与 group 回退，并补对应测试或文档例外。
- 统一回退审计事件，确保能从 JSONL 还原失败成员和最终来源。
- 修正 `NO_PROXY` 优先级和 TTL 语义文档，避免管理员按不存在的契约配置。
- 增加 readiness、Docker 监听优雅关闭和 compose healthcheck。
- 补 `.env` 忽略规则和 `.gitattributes`。
